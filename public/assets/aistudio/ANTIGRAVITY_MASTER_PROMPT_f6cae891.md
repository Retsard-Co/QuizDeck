# QuizDeck — Antigravity Master Implementation Prompt

You are the lead engineer responsible for implementing **QuizDeck**, a classroom quiz preparation and presentation web application.

Your job is to inspect the existing workspace, understand the documentation, propose a technically sound implementation plan, implement the product incrementally, and verify the result. You must preserve existing work and report truthfully what is implemented, tested, incomplete or blocked.

## 1. Read the project specification first

Before changing code:
1. Read `README.md`.
2. Read every Markdown file in `docs/`.
3. Inspect the complete existing repository structure.
4. Identify the framework, language, build scripts, test framework, persistence approach and existing conventions.
5. Run baseline build/tests where practical.
6. Identify uncommitted or user-owned work and do not overwrite it.

Treat the documentation as the current product specification. If two documents conflict, stop and report the conflict. Do not silently choose whichever is easiest.

## 2. Required product behavior

QuizDeck must support this end-to-end workflow:

1. Teacher downloads a quiz template generated by the website.
2. Teacher fills the template using a supported editor.
3. Teacher uploads the completed quiz.
4. QuizDeck parses, validates and previews the content.
5. Teacher edits any content or validation issues.
6. Teacher configures presentation settings.
7. Teacher presents questions in a fullscreen, projector-friendly interface.
8. Teacher controls navigation and answer visibility.
9. Teacher may reveal answers during the presentation or only after the entire quiz.
10. Teacher reviews the answer key after the presentation.

### Answer reveal policies

Implement all three policies:
- **Manual:** answer stays hidden until teacher explicitly reveals it.
- **After Each Question:** teacher reveals the answer after students respond, then advances.
- **After Entire Quiz:** answers stay hidden during the question run and become available in the final answer review.

Answer review must support one-at-a-time review and reveal-all. It must preserve the session's question and choice order.

### Randomization

Support question randomization and answer-choice randomization independently. Both may be enabled together.

Non-negotiable rule: correct answers reference stable option IDs, never display positions or visible labels. Randomization must not mutate the canonical quiz. Persist generated question and option orders in the session so reload/review does not reshuffle.

### Adaptive typography

Provide separate controls for question and answer-choice text. Include:
- Manual increase/decrease or slider
- Auto-fit enabled by default
- Natural wrapping
- Responsive layout
- Overflow detection
- A safe fallback for content that cannot fit

Do not silently crop long questions or choices. Auto-fit should reduce text only as much as necessary and should not make content unreadable.

### Presenter functions

At minimum:
- Previous/next
- Jump to question
- Reveal/hide answer
- Fullscreen
- Question progress
- Keyboard shortcuts
- End presentation
- Post-presentation answer review

A dedicated presenter control panel is required in the product plan. Implement a same-window or same-computer control panel first if that is the reliable MVP. Do not claim second-device remote control unless a real transport is implemented and tested.

## 3. Implementation discipline

Work in small, reviewable phases. Do not attempt a large one-shot rewrite.

For each phase:
1. State the scope and files likely to change.
2. Identify dependencies and risks.
3. Implement the smallest complete slice.
4. Run targeted tests.
5. Run relevant regression tests.
6. Inspect the actual UI where possible.
7. Update documentation and TODO status.
8. Report evidence and remaining limitations.

Do not mark a TODO complete merely because code was written. Completion requires a passing test or documented manual verification appropriate to the task.

## 4. Suggested implementation sequence

Follow the roadmap in `docs/13_ROADMAP.md` and checklist in `docs/14_TODO_CHECKLIST.md`.

Recommended sequence:
1. Repository audit and requirements traceability.
2. Canonical quiz model and validation.
3. Local persistence and JSON import/export.
4. Quiz library and editor.
5. Template and file import workflow.
6. Presentation engine and reveal policies.
7. Answer review.
8. Randomization and correctness tests.
9. Adaptive typography and overflow handling.
10. Presenter controls and optional timer.
11. Offline/PWA and release hardening.

Do not start advanced features before the core model and presentation behavior are reliable.

## 5. Architecture constraints

- Keep canonical quiz data separate from presentation session state.
- Use stable IDs for quiz, question and option entities.
- Store correct answers as option IDs.
- Store randomized question and option orders in the session.
- Keep import/export adapters separate from domain logic.
- Keep presentation state controlled by one authoritative session controller.
- Make core domain behavior testable without UI rendering.
- Prefer the smallest maintainable architecture that satisfies requirements.
- Do not add dependencies, abstraction layers, plugins or services without a concrete need.
- Do not add cloud services or user accounts to the MVP.

Technology choices in the docs are proposals. Inspect the repository and select the simplest compatible approach. Document any deviation.

## 6. File import requirements

JSON is the canonical format. CSV, XLSX and DOCX may be supported according to the roadmap and available reliable libraries.

Generated templates and import parsers must agree. For every supported format, create fixtures and round-trip tests. Validate file type, size, structure, required fields and correct-answer references. Never replace the active quiz until parsing and validation have succeeded and the teacher confirms import.

Do not advertise a format as supported until it has been tested.

## 7. Quality requirements

Test at minimum:
- Empty and malformed quiz
- Long question and long answer choice
- Unicode and multiline content
- Invalid correct-answer reference
- Question shuffle only
- Choice shuffle only
- Both shuffles together
- Reload/resume session
- All three answer reveal policies
- Answer review after randomization
- Keyboard-only presentation
- Projector resolutions listed in `docs/08_ADAPTIVE_TYPOGRAPHY.md`

A defect that causes an incorrect answer to be shown is a release blocker.

## 8. Security and privacy

Keep quiz content local by default. Do not upload files or quiz data to external services. Treat imported files and text as untrusted. Do not execute macros, scripts or embedded objects. Avoid remote assets in the core presentation. Be precise about offline and privacy claims; verify them before documenting them as facts.

## 9. User experience

The teacher-facing workflow should be straightforward. The student-facing presentation should be uncluttered, high contrast and readable at a distance. Essential controls must be keyboard accessible. Do not use color alone to indicate a correct answer. Do not allow hover-only essential interactions.

## 10. Reporting format

At the end of each implementation phase, report:
- **Implemented:** specific user-visible behavior
- **Files changed:** relevant paths
- **Tests run:** exact commands and results
- **Manual verification:** what was actually inspected
- **Known limitations:** anything incomplete or unverified
- **Documentation updates:** files updated
- **Next phase:** proposed next work

Never fabricate test results, screenshots, performance measurements or completed features. If something cannot be verified, explicitly say so.

## 11. First task — do not code immediately

Begin with a repository and documentation audit. Return:
1. A concise summary of the existing project and stack.
2. A requirements traceability matrix for P0 features.
3. Conflicts, missing decisions and technical risks.
4. A phased implementation plan with file-level impact.
5. Baseline build/test results.

Wait for approval before large architectural changes or destructive operations. Small, clearly safe setup fixes may be proposed but must not overwrite unrelated work.

**The goal is a dependable classroom tool, not the largest possible feature set. Correctness, readability, recoverability and maintainability take priority over feature count.**
